# Ontological: Build plan

This file turns [ARCHITECTURE.md §12](ARCHITECTURE.md#12-build-plan-and-verification) into ordered work. §12 owns the milestone list, each milestone's scope and its "done when" criteria. This file owns the order: spikes, tasks, dependencies, and what each milestone hands to the next. If the two disagree, fix whichever is wrong in the same commit.

Task IDs (`S3`, `E2`, `M1.4`) are stable, so commits and issues can refer to them. `after:` lists the tasks that must finish first. **TDD** marks work that is written test-first (see [Test-first work](#test-first-work)).

## How the order was chosen

1. **Unverified claims go first, as spikes.** Each spike answers one question, has a decision rule written before it runs, and either confirms the architecture or names the section to change.
2. **One thin vertical slice before any depth.** The riskiest parts are the Agent SDK behaviour behind the gated agent (§8.1) and the eval loop. M1 runs both end to end on Chinook, headless, before the catalog, compile or UI get deep.
3. **The eval set exists before anything depends on it.** M3's retrieval benchmark needs gold SQL, and M4's tuning needs end-to-end scores, so the question set is frozen in M0.
4. **Usage is a budget.** Every eval run comes out of the user's subscription. Development runs use the 20-question smoke set with the answer agent on Sonnet. Full runs on the real routes happen only when a default is being set.
5. **The engine comes before the UI.** The eval runner, the MCP shim and the Electron app are all clients of the same engine API, so the API settles in M1 and M2 before the Electron work in M2 starts building on it.

## Eval set

The eval is a scoreboard for this project, not a reproduction of anyone's benchmark. It answers two questions: did a change make answers better or worse, and which setting should be the default.

### Questions

| Set | Contents | When it runs |
|---|---|---|
| **Dev** (76) | 36 of the 41 Wide World Importers questions (the other 5 have gold SQL that returns no rows on the data; M0.8), plus 40 BIRD Mini-Dev questions: 10 each from `financial`, `california_schools`, `formula_1` and `debit_card_specializing`, sampled to Mini-Dev's own simple / moderate / challenging mix | Tuning rounds; full runs when a default is being set |
| **Held-out** (40) | 40 further Mini-Dev questions from the same four databases: `debit_card_specializing` has only 14, so it gives 4 and the other three 12 each | Once per milestone, for the winning configuration only |
| **Smoke** (20) | 10 WWI and 10 BIRD questions taken from dev | Day-to-day development, with `answer_agent` pinned to Sonnet |

Why these four BIRD databases: `financial` and `debit_card_specializing` are transaction data close to what users will point the tool at, `formula_1` has many tables and long join paths, and `california_schools` has column names with spaces and abbreviations that exercise the identifier tokenizer. WWI is a sales and warehouse database with checked gold SQL.

Rules:
- `eval/sets/{dev,heldout,smoke}.json` holds question IDs only, chosen by a script with a fixed seed. Nothing in `eval/sets/` changes once M0 ends unless a question turns out to be broken, and then the change is a commit of its own with the reason.
- The data is downloaded, never committed. BIRD is CC BY-SA 4.0. The WWI DDL and CSVs come from `datasets/wideworldimporters/` in [ontology-sql-eval](https://github.com/NVIDIA/ontology-sql-eval/), MIT-licensed from Microsoft's samples.
- BIRD questions include their `evidence` text, as the benchmark defines them. BIRD's `database_description/*.csv` files and ontology-sql-eval's extra custom analyses are not ingested, so the score measures Ontological's own compile.
- The eval passes each question's database as the scope (§8.1), as the reference harness routes by `db_id`.
- Later (M5): answers the user marks correct on their own data can be saved as eval cases. They form a separate personal set and never replace the frozen ones.

### Scoring and runs

- **Execution accuracy** uses BIRD's rule (compare result sets), ported from the verifier in ontology-sql-eval (Apache-2.0). Gold SQL runs on the source natively: `sqlite3` for BIRD and the eval Postgres cluster for WWI. Ontological's SQL runs through its own source executor.
- **Dialect artifacts.** BIRD's gold SQL runs on SQLite, while Ontological's SQL runs on DuckDB, and the two differ on some semantics (integer division is the common one). The verifier logs every mismatch where the rows agree after numeric normalization; these get one hand review in E4 and a fixed tolerance rule after that.
- **Control arm.** A schema-only baseline: one structured call per question with the question and a schema dump, no tools, on the same model as the agent. It runs once per model per set, not once per configuration.
- **Recorded per run:** execution accuracy, share of answers the gate verified, spawns and turns per question, per-model tokens, the `utilization` change, and the resolved model IDs. Eval configs pin full model IDs (§6.3), so a model release can't land in the middle of a comparison.
- **Variance.** LLM output isn't repeatable, so "reproducible" means one command, pinned data, pinned model IDs and stored results. With about 80 questions only differences of about 10 points stand out from noise. When two configurations land within that range, the cheaper one wins.

### Tuning rounds

A round is 3 full dev runs: the current baseline, the critic off, and `answer_agent` on Sonnet. The first round in M4 adds a fourth run, `answer_agent` at `high` effort (§6.3 starts it at `medium`). After the round, the winner runs once on held-out.

Compile settings (`compile.table_calls`, the compile routes, the embedding model) are not tuned with full eval runs. They are judged by the compile-quality review and the retrieval benchmark (§7.4), which cost no quota once a compile exists. Only a finalist gets a full run.

### Usage

Estimates at API prices, as a way to compare runs. They are not a statement about subscription quota, which Anthropic doesn't publish. S3 replaces them with measured numbers.

| Run | Question-runs | API-equivalent |
|---|---|---|
| Smoke, agent on Sonnet | 20 | ~$5 |
| Dev, real routes | ~80 | ~$40–50 |
| Tuning round (3 dev runs + held-out) | ~280 | ~$170 |
| Control arm, per model | ~120 | ~$10 |

The smoke score in M1 only needs to exist. It will be low, because BIRD and WWI need M2's Postgres source and M3's full compile.

**M1.4 decided (2026-11-06): the minimal compile.** `engine/ontological/compile/` runs one table at a time in upstream's canonical order and awaits each Claude call before the next. `table_keys`, `column_descriptions` (15 columns to a call) and `table_terms` send upstream's system prompts and JSON schemas unchanged, with `prompt_version` set to upstream's commit, `2a24f5d`. Three things differ from upstream on purpose:
- The keys prompt names the table's declared primary key. Upstream reads it from a work list that never carries it, so its prompt always says "(none)".
- The keys prompt reads the columns after profiling has stored their samples, so it has them on a first compile. Upstream reads them before profiling.
- The terms prompt lists every candidate column. Upstream stops at 40, and chunking stays M3.2's.

Profiling sends its queries through the executor's `probe` and computes the statistics in the engine. JSON key paths, the mixed-date-shape warnings and the move into the executor wait for M2.5. Synonyms (`table_synonyms`) wait for M3.2, and Chinook has no table descriptions for them to read anyway. Semantic FKs come from declared FKs only. Where a table has several FKs to the same attribute, the join default is upstream's deterministic fallback, the first column by name. Upstream embeds each table's Terms as it writes them, and nothing here embeds: M1.6 builds dense retrieval over Terms and attributes, so it writes those vectors.

Upstream's fallbacks only cover an answer that fails validation. When Claude doesn't answer at all (a rate limit, an overload, a logged-out or missing `claude`, a failed spawn), compile stops before writing the table it is on. That table and the rest stay in the work list, and the next run resumes there. Otherwise a fallback Term would be committed and the table would never be compiled again. M3.1 adds the pause until `resets_at`.

**M1.6 decided (2026-11-06): the semantic layer is synced after the compile, and the pack makes no Claude call.** `compile_database` takes the embedder and, once its tables are written (or it stops), syncs the database's Terms and attributes into `semantic_layer` (`ontological/embed/semantic.py`) with upstream's row texts. Upstream embeds each table as it commits and appends. The sync instead embeds every row whose text or model has no vector yet, in the embedder's token-capped batches, and deletes the vectors of rows that changed or are gone, so a stopped or failed run is caught up by the next. The grounding pack (`ontological/answer/`) ports the deterministic half of upstream's `candidates_retrieval.py` and `candidates_preparation.py`: per-entity dense search, the database chosen by coverage with uncovered entities searched again, the attributes' store context, their tables and the subject Term's, and `find_join_path` (vendored unchanged) from the anchor to each other attribute's table. Upstream's LLM steps are dropped: there is no intent or relevance filter, and the anchor is `plan`'s or else the nearest attribute. Before the agent extracts entities, the raw question is the one entity and searches 10 attributes, but only each entity's nearest 2 rank the databases, as in upstream; counting all 10 let the database with the most middling hits beat the one with the nearest. M4.3 calls this from `plan` and puts M3.6's hybrid search under it in place of the dense one. SQL attributes (M3.5) and saved analyses (M5.3) join the search once something writes them; junction and bridge-table expansion isn't ported yet.

**M1.7 decided (2026-11-06): the gated agent.** `ontological.answer.ask()` takes the grounding pack and opens one `answer_agent` session through `ClaudeGateway.agent()`, which allows the session's SDK MCP tools and nothing else and carries `AnswerModel` in `output_format`. `AgentRun` yields the model's text and each tool call as they happen, and keeps the tool log. Each tool result has a `data` record that the gateway keeps from the model, and the post-run check (`answer/postcheck.py`) reads it. A Claude call made from inside a tool, such as the critic's, reuses the session's slot, because taking a second one would deadlock at a concurrency of 1. Sessions are logged in `ops.llm_call` as kind `agent` (migration 0006) and never cached.
- **Preconditions.** Every tool but `plan` refuses until a plan exists, as "must be the first call" implies; §8.1's table now says so. `plan` refuses a database other than the session's. `run_sql` needs a `validation_id` that passed. `review_answer` needs the critic on and a `validation_id` that ran, and with the critic off it isn't offered at all. The caps are upstream's: 7 `validate_sql` calls and 2 reviews. Arguments that fail a tool's input schema are refused by the SDK before the handler runs, so they don't appear in the log.
- **The gate, checks 1–3.** Checks 1 and 2 are new. Upstream only validated SQL its own graph generated, and its `parse_query_single` drops a table or column it can't resolve instead of naming it. Here every table is resolved first, then every column through sqlglot's `qualify`, and the issue names what is missing, with the nearest catalog tables or the table's columns. A database qualifier (`chinook.main.Album`) is refused, because the executor attaches the source under its own alias. Check 3 is upstream's degenerate-SQL and missing-aggregation checks, with upstream's messages. Upstream's vacuous GROUP BY check isn't ported: upstream ships it off. `TableEntry` now keeps the columns' spellings, so the messages name columns as the catalog spells them.
- **The critic** is upstream's intent validation (system prompt, prompt body and model) on `answer_review`, shown the pack's join paths as its authoritative ones, plus the result's first 20 rows and the draft answer, which upstream's validation never saw. A critic that doesn't answer passes the SQL unreviewed, as upstream's does, and `reviewed: false` records it.
- **The system prompt** has the tool steps, S1's refusal line, upstream's nine calculation subtypes (names and descriptions), the pack, and upstream's SQL rules with a DuckDB note. The slots for example queries and join paths are dropped, because the pack shows the join paths. Prompt content is tuned against the eval, not here.
- **Left for later.** M4.3 has these: `plan`'s per-entity retrieval and the subtype's SQL template, withholding `run_sql` and `review_answer` from `information` questions, `plan`'s refusal of `prediction`, source choice without a scope, and the restart. The post-run check already applies the intent rules to whatever intent the plan recorded, and since the model picks the intent and can re-plan, an `information` or `answerable=false` answer is unverified when it carries SQL or when `run_sql` returned rows in the session. Upstream's subtype templates are BIRD dev queries over `gasstations`, `posts`, `superhero`, `financial` and others, so M4.3 should check them against the eval's four BIRD databases before showing them. `AnswerModel` has no `chart` yet; it comes with M4.6's ResultChart port.

**M1.8 decided (2026-11-06): one question is one `POST /ask`, answered whole.** The route takes `{question, database, critic}` and returns once the session ends, with no stream: the answer, `verified` and the post-run check's `reason`, `sql` (the answer's SQL as `validate_sql` passed it, matched by `validation_id`, or null), `result` (what `run_sql` returned for that id: columns, types, at most 200 rows, `truncated`), `steps` (the tool log, each call's `data` included) and the session's `outcome`, `error` and model. `StoreAnswers` (`answer/service.py`) finds the source in the database's catalog row, as compiles do, builds the pack with the database as its scope, and opens a source executor for that one question. A database with no source is 404; an engine without the embedding model is 503. `ontological ask "<question>" --source <database>` holds a lease through the MCP shim's `hold_engine`, starting an engine headless if none runs, and passes options it doesn't know to that engine, as the shim does, so M1.9 can start one with `--app-data <eval home>/app`. It exits 0 for a verified answer, 2 for an unverified one and 1 when it couldn't ask. The streamed steps, re-attach and cancel are M4.5's (§8.4).

**M1.9 decided (2026-11-07): the eval runner.** `uv run python -m ontological_eval run <set>` in `eval/`; the `ontological` CLI can't import the eval package, which depends on it. Each config in `eval/configs/` pins full model IDs for `answer_agent` and `answer_review`, and the runner refuses an alias.
- **The agent arm goes through the engine.** The engine takes `--routes FILE`, and the runner starts one on the eval store with the config's routes, holds one lease, and asks each question with `POST /ask`, the question's database as the scope. A BIRD question's evidence goes in the question text. The runner refuses while another engine serves the store, since its routes may differ, and stops the engine it started.
- **Scoring** ports ontology-sql-eval's `exec_match.py` at `ec41b2c`: `set(gold) == set(pred)`, with its failure codes and its 5% `no_model_output` guard on reporting a score. Gold runs natively. The agent's SQL runs through the source executor's new `fetch`, up to 100,000 rows. Each query gets its own 60 s limit rather than BIRD's shared one, and a gold failure scores zero and stays in the denominator, as BIRD scores it.
- **Dialect artifacts.** The tolerance check rounds numbers to 6 significant digits and writes dates and times as ISO text. A miss that matches after that is flagged and still scores zero until E4. The first live run found one already: DuckDB reads `CAST(x AS REAL)` as float32 (0.5714285969734192 against SQLite's 0.5714285714285714).
- **The control arm runs natively**, as ontology-sql-eval's schema-only arm does: the database's own DDL (`sqlite_master`, WWI's `ddl/*.sql`), their user turn, a structured `{sql}` answer in place of their fenced block, on the agent's route through the runner's own gateway, which never serves from the cache. So it writes the dialect its schema shows, and needs no engine. Its answers are stored per model and effort, and a run asks only about questions without one, which keeps it to once per model per set.
- **Usage.** A question's calls are the engine's `ops.llm_call` rows logged while it ran; rows for other tasks are counted apart and flagged. Tokens split each call's `model_usage` into the model that answered and Claude Code's side calls. Utilization is the change in `raw["unifiedWindows"]` between the runner's pings before the run and after each arm. The first runs reported only `seven_day`, in steps of 0.01, so S3 needs more than a few questions to see a change.
- **Stored** in `<eval home>/results/runs/<run id>/`: `run.json` (written after every question), `routes.json` and `report.md`.
- The eval store, ingested before M2.6, had no source recorded for its databases, and `/ask` answered 404. Running `ingest` again records them; the runner's 404 says so.

**M2.4 decided (2026-11-06): monthly counts get a table of their own, and the engine counts while the pool parses.** `public.sql_query` has no column for upstream's per-month counters, and §5.2 keeps `public` as upstream has it, so they go in `app.sql_query_month` (one row per statement and month) in Ontological's chain. `query_stats.py` writes and reads one key, `count_monthly_YYYY_MM`, and orders months by (year, month); the vendored `Query` model writes it too. `ontological.catalog.query_history.ingest_query_history(database, rows, dialects=, pool=)` takes upstream's `get_queries` records: the engine counts repeated texts once, the pool parses each distinct text and folds those with one shape together (upstream's five gates plus its normalized SQL, as a dict key), and the engine matches them against the store by text, then by shape, with the pool normalizing the stored candidates. **M2.3 decided (2026-11-06): a re-ingest is one transaction, and upstream's denylist test isn't ported.** Upstream diffs each schema on a thread pool and commits each write on its own, so a failure part way leaves a half-diffed catalog until the next ingest repairs it. **M2.5 decided (2026-11-06): ingest profiles, then builds the data layer.** Upstream profiled at compile and embedded the data layer at ingest, so the texts never had sample values. **M2.2 decided (2026-11-05): a Postgres source cancels on the server.** DuckDB's `interrupt()` doesn't reach a query the `postgres_scanner` or `mysql_scanner` is waiting on, so §5.6's kill would be the only cancel, and a killed child left Postgres running its query. **M3.1 decided (2026-11-06): a compile is a job, planned once.** `compile_database` runs as a row in `ops.job` with one `ops.job_step` per table, planned when the job starts from the tables with no Term: canonical order, and a pack for each step (`compile/packing.py`). A table's Terms, attributes and step commit in one transaction, so a crash can't leave a table written but its step pending, or the reverse. The next run resumes the database's unfinished job on the steps it began with, never a fresh plan of what is left, so the packs, and their cache keys, are the ones the first run used. A rate limit or an overload pauses the job (`paused_until` is the gateway's `resets_at`, or a minute from now when there is none) and retries the table 5 s after that. A job a new engine finds paused waits out the rest of the pause before it asks anything. Any other unanswered call (a logged-out or missing `claude`) stops the job with its error, for the next run to resume. The engine counts the jobs it is running in memory (`jobs/active.py`), paused ones included, for idle shutdown, so a job a crashed engine left `running` in the table doesn't keep a new engine up. Packing follows §6.4's numbers: a table with at most 6 columns is small, and small tables fill packs greedily in canonical order up to 8k tokens, estimated from column counts (150 a table, 100 a column) because the plan comes before profiling. A pack holds one schema's tables, and a wide table is a pack of its own outside the run of small ones, so adding a wide table, or changing another schema, moves no small table's pack. Compile still sends one table to a call: M3.2 sends the packs and calibrates the estimate.

**M3.2 decided (2026-11-06): each stage asks once a pack, and a pack commits whole.** Compile runs the plan's packs in the order of their first tables. For each pack, it profiles every table, then runs `table_keys`, `column_descriptions`, `table_terms` and `table_synonyms` once for the pack, then writes the pack's tables and their steps in one transaction. A resumed pack therefore makes the same calls, and the cache answers the ones already answered. Tables now commit in plan order, which is deterministic but no longer strictly canonical across packs. A packed call (`compile/packed.py`) sends each table's own prompt under its `Table:` line, the stage's system prompt with a note on answering per table, and a schema with one entry per table, under `prompt_version` `2a24f5d+pack.1`. Upstream's prompt goes out unchanged for a table that is alone in its pack in having something to ask (a wide table always is). It also goes out for a table the pack's answer leaves out or answers invalidly: that table is asked alone instead of taking the fallback, so packing never trades quality for calls. Descriptions batch a pack's undescribed columns 15 to a call and never split a table. On Chinook the compile drops from 30 calls to 16. A table with more than 40 candidate columns is asked for its Terms in chunks of 40, upstream's cutoff. Each later chunk lists the Terms proposed before it, Terms with one name merge, and an invalid chunk leaves its columns to the first Term. `table_synonyms` ports upstream's synonym call for tables with a description. Upstream skips it when the terms call fell back; here it is asked anyway, since it reads only the description. The certified-description guard is in the vendored DAL: `upsert_table_term` keeps a Term's description when `description_certified` is set, and `merge_column_attribute` keeps a certified attribute's description. The pack estimate is calibrated on Chinook's keys prompts, the largest each table gets: 100 tokens a table and 60 a column, down from 150 and 100. The run is still sequential: one call at a time.

**M3.4 decided (2026-11-06): one pick call per 25 columns, asked before any inferred edge is written.** After the packs, compile syncs the semantic layer's vectors and then resolves semantic FKs (`compile/semantic_fk.py`), first of M3.5's post-stages, since bridge detection reads them; the vectors are synced again after the post-stages, for their SQL attributes. The FK stage: it writes declared FKs as before, then takes the other unlinked columns in canonical order (table, then column, casefolded). Each column gets upstream's candidates: two dense searches of 3 (name and description, then name alone) for unique attributes of the database, merged, with the column's own table left out. One `semantic_fk_pick` call goes out per 25 columns that have candidates, each column under its own `Foreign-key column:` line, with upstream's prompt for that column, under `prompt_version` `2a24f5d+batch.1`. A column alone in its batch gets upstream's call unchanged. So does a column the answer leaves out, answers with an id it wasn't offered, or that shares its heading with another column of the batch. For a column Claude passed on, the sample-match probe looks for a same-named candidate holding every one of its sample values. Then every edge whose column shares no value with its target, or is all NULL, is pruned, declared edges included. Both probes go through the executor's `probe` op (5 s timeout) in DuckDB's SQL, and a refused or timed-out probe leaves the edge alone. Upstream's overlap query reads its two counts from a UNION ALL, whose row order DuckDB doesn't promise, so ours reads them from one row. Every pick is made before any inferred edge is written. If Claude stops the stage, the job is `stopped` with its steps done, and the resumed job asks the same batches, which the cache answers. A rate limit pauses and retries the stage like a pack. Inference runs only for a job that planned tables. Otherwise a column Claude passed on, or one whose edge was pruned, would be asked again by every compile, in a batch the cache has never seen, so a compile with nothing new makes no calls. Without an embedder, only declared FKs get edges. FK calls are logged under the job with no pack (`table_name` "semantic FKs"). Join defaults still take upstream's deterministic fallback; the model call for a table with several columns pointing at one attribute isn't made yet.

**M3.8 decided (2026-11-06): the screen reads jobs from the store, and a table's stages from its calls.** Every Claude call is logged under the job and the pack it was for (`ops.llm_call.job_id`, `pack`, and `table_name` naming the pack's tables, set by `llm.calls.call_scope`, which compile enters per pack), and a cache hit now writes a `cached` row with no output that is never served itself, so a job counts its spawns and its cache hits apart. Since M3.2 one call answers for a pack's tables, and a pack's steps are checkpointed only when it commits, so each pending table's tile counts the stages its pack's latest try got through from those rows (`jobs/view.py`, `stages_done`): the cache holds those answers, which is what "checkpointed" means on the tile. The bar has a segment per stage: keys, descriptions, terms, synonyms. A person's pause is a new job state, `held`: compile stops before its next pack, or at once while it waits out a usage limit ("Don't resume"), and waits for Resume. The engine now builds the one Claude gateway and runs compiles as tasks on its loop (`jobs/service.py`): `POST /jobs/compile` starts or resumes one, `/jobs/{id}/hold`, `/resume` and `/dismiss` act on one, and at start it resumes every compile an earlier engine left `running` or `paused`, so a paused compile really does pick up by itself. A held or stopped one waits for the person. M2.6's refreshes are recorded as `ingest` jobs with the tables they found, which the rail offers to compile until the person picks Later. The renderer polls `/jobs` every 2 s. Left for later: the estimate card is M3.7's; "slowed to 1 at a time" needs §6.5's `allowed_warning` concurrency drop, which the gateway doesn't make yet; the usage meter, notifications and the dock badge need the gateway's status exposed; "New compile…" and "Ingest metadata" in the header wait for a source picker; auto-compile still waits for `app.setting`.

**Auto-compile decided (2026-11-07): the setting lives in `app.setting`, and the engine's loop starts the compile.** `app.setting` (Ontological's revision 0008) keeps one JSON value per key, and a key with no row takes its default from `ontological/settings.py`. The first key is `compile.auto_compile`, off by default. The staleness check passes each recorded refresh that found new tables to `Jobs.auto_compile` on the engine's loop and waits for the answer. With the setting on, that starts the database's compile, as Compile on the Jobs prompt would, and dismisses the refresh's prompt. With it off, the prompt waits for the person as before. It also waits when that database has an unfinished compile (running, paused, held or stopped), or its source has gone. Resuming a compile runs only the tables it planned, which leaves out the new ones, and a held or stopped compile waits for the person. A refresh that ends after the engine has begun stopping starts nothing. Settings → Compile has no toggle yet, and the engine has no settings route, so the setting can only be changed in the store for now. `compile.table_calls` (M3.3) and the PII toggle (M3.5) can now be keys here too.

**M3.3 decided (2026-11-06): merged is one call a table, and anything it can't answer takes split.** `compile_database(..., table_calls="merged")` (the `compile.table_calls` setting, which waits for `app.setting`) asks each table one `table_semantics` call (`compile/merged.py`, `sonnet`/`high`, `prompt_version` `2a24f5d+merged.1`) in place of the four stages. Its system prompt is the four stages' system prompts verbatim as numbered sections, with a note on how they fit together; its user turn is each stage's own prompt for the table under the same numbers, and a section with nothing to ask says so. The answer (`TableSemantics`: upstream's keys answer plus `column_descriptions`, `terms` and `synonyms`) goes through each stage's own clean-up, so the store ends up with what split writes for the same answers. Since one call can't read its own answer, the descriptions and Terms sections list every column that isn't a declared FK, and a column the answer suggests as an FK is dropped afterwards, as split leaves it out; the Terms section shows only the descriptions columns already had. Merged doesn't pack: §6.4 counts one call a table, and packs still set the commit and resume unit. Three kinds of table take the split stages instead: one with more than 40 candidate columns, which split asks in chunks; one with no candidate columns, for which split asks only its keys; and one whose answer is invalid, which is asked split's calls rather than taking their fallbacks. The option applies to the tables a run compiles, so a resumed job can take the other one. On Chinook a merged compile makes 10 table calls, one for each table but PlaylistTrack, which has nothing to ask, where split makes 15; the post-stages after them are the same for both. The test's script answers Genre invalidly, which adds Genre's 3 split calls to merged and 1 to split.

**M3.5 decided (2026-11-06): the post-stages run on every compile, and PII moves from ingest to compile.** After the declared semantic FKs, `compile_database` runs the SQL-attribute judge (`compile/sql_attributes.py`), the bridge stage (`compile/bridges.py`) and, with `pii` on, PII detection (`ontological/pii/`), then carries PII tags to the attributes of tagged columns, on or off. A rate limit pauses the job and reruns the stage. Any other unanswered call stops the job, and the next run resumes it. A person's hold (M3.8) takes effect before a stage or during a pause, and resuming runs the post-stages again. Their calls are logged under the job with no pack, named by stage (`SQL attributes`, `bridge tables`, `PII`), so the Jobs screen's per-table stages are unchanged. A rerun skips what earlier runs wrote, because attribute names and SQL are taken, bridges with an attribute are no longer candidates and classified columns are `pii_processed`. **`_usage_score` is fixed** by M2.4's `app.sql_query_month`. A statement scores its count over the three calendar months that end with the latest month in the database's history, and a fragment scores the sum over its statements, with all-time counts breaking ties. The window is anchored to the history, not to today, so a history read long ago still ranks. It is one window for every statement, not each statement's own three latest months (`query_stats.recent_usage`), so a statement that was busy two years ago and has been idle since can't outrank one used this month. The parse pool extracts the fragments. The judge asks up to 10 Terms (about 24k characters) a call under `prompt_version` `2a24f5d+judge.1`. A lone Term, or one the answer leaves out, gets upstream's prompt unchanged. Each kept fragment is wrapped in a SELECT (upstream's rules) and checked as upstream checks it, by resolving its tables against the catalog. Compile has no connector dialect, so the check uses upstream's fallback for that case, `["", "postgres"]`. Its statement is a `sql_query` with no sightings, or the history statement with the same text, as upstream's upsert matched it. Only Postgres sources keep a history (M2.4), so only they get these attributes. **Bridges** go to `bridge_sql` on Opus, one call each. With one candidate Term the prompt is upstream's. With several, the same call lists them and names the owner (`2a24f5d+owner.1`), in place of upstream's rerank, and a name that matches no candidate falls back to the first, as upstream's rerank failure did. Every bridge is marked a junction first, so Chinook's PlaylistTrack now is one. **PII** runs at compile, not at ingest as upstream's does. Ingest has no gateway and nothing to pause on a limit, and by compile the classifier can read the columns' new descriptions. It is off by default, as upstream's flag is, until `app.setting` carries the Settings toggle. The rules are upstream's unchanged. Up to 40 uncertain columns share a `pii_classify` call (`2a24f5d+batch.1`), each sent only as its name, its table's name and its description. Each call's columns are tagged and marked as soon as it answers, and a column whose answer was invalid stays unprocessed for the next run. The semantic layer now syncs SQL attributes with upstream's text. Retrieval doesn't search them yet; M4.3's `plan` adds them.

**M4.2 decided (2026-11-07): an empty result is `run_sql`'s second outcome, with the literal check run again.** The probe cap (40 probes of at most 50 rows a question) and the statement timeouts (5 s a probe, 60 s for `run_sql`, which interrupt the query and come back as a `SourceError`) were already built by M1.2 and M4.1. What M4.2 adds is in `AnswerTools.run_sql`: its result carries `outcome`, `rows` or `empty`. An empty result isn't `is_error`, since it can be the answer, so it counts as a run for review and the post-run check. Its text tells the model it got no rows and to recheck its filters and literals before answering. It reruns check 5 with `result_was_empty`, so a literal on a column of more than 20 values, which the gate leaves alone, is point-probed for case and whitespace variants (a fuzzy spelling near-miss still needs a column of 20 values or fewer), and passes on the fixes it finds as `repairs`. Those probes share the gate's `ProbeExecutor`, so its cap. The post-run check is unchanged: an `information` or `answerable=false` answer after an empty run is still unverified, since "the data has nothing on it" is what a wrong literal says. **The drop-LIKE rerun followed (2026-11-07).** When the empty SQL filters with LIKE or ILIKE, `ontological/answer/like_check.py` puts TRUE in place of each such filter that reaches its WHERE, HAVING, QUALIFY or JOIN ON through AND, OR and parentheses alone, where TRUE can only let rows through, and runs the result as one probe on the same `ProbeExecutor`. A filter under a NOT or inside a CASE stays. If rows come back, the result's `without_like` holds the filters dropped and the first 5 rows, and its text says the LIKE filtering emptied the result. Upstream asks a model which LIKE predicates are non-essential and routes the SQL back to be rewritten without them; here the probe makes no model call, and the model reads the rows and decides which pattern to fix.

**M5.1 decided (2026-11-06): an edit is logged field by field and undone as an edit.** `ontological/curate/edits.py` has `edit_term` (name, description, synonyms and the two certification flags), `edit_attribute` (name, description, certification), `undo` and `history`. An edit locks its row, writes the fields that differ from the stored ones through the vendored DAL (`update_term`, so a rename also rewrites the attributes' `term_name` copy, and `update_column_attribute`), and writes one `ops.change_log` row per field, sharing an edit id, in the same transaction. `old` and `new` are JSON. A field set to what it holds isn't a change, and an edit that changes nothing writes nothing. A rename onto a Term's name that is taken is refused before anything is written. Given the semantic layer's VDB, the edit then runs `sync_database` on the entity's database, which re-embeds only the texts whose content hash changed: a description edit one vector, a synonym edit the Term's attributes (their text names the synonyms), a rename the Term and its attributes. Those writes rebuild the BM25 index through `on_change`. Each semantic vector's metadata now says whether it is `certified` (a Term when its name and description both are), for hybrid search's bonus. A certification changes no text, so the sync rewrites the flag in the vector's metadata and embeds nothing. An undo writes each field's old value back as a new edit whose rows name the one they revert (`undoes`), so undoing an undo makes the edit again. An edit is undone once, and not while a later edit holds one of its fields. A change of embedding model re-embeds as a `reembed` job (`ontological/embed/reembed.py`): one `ops.job` row per database whose vectors name another model, no steps, since the sync embeds only what still lacks a vector from the new model, counted in `ActiveJobs`, and resumed by the next run after a crash or an error. It syncs the semantic layer, then replaces the data layer. Once it serves, the engine starts one for each database with vectors from a model other than its embedder's (`Jobs.reembed_stale`), skipping one already re-embedding, and Settings → Embeddings shows the model and those databases and has Re-embed, which does the same (`GET /embeddings`, `POST /jobs/reembed`). Compile and import log their writes too (below).

**M5.2 decided (2026-11-07): the graph is the join graph, drawn as DOM buttons.** The engine reads the ontology in `ontological/curate/ontology.py` and serves it through `api/curate.py`: `GET /sources/{id}/terms` (the glossary, with how many Terms are certified, name and description both), `GET /terms/{id}` (tables, attributes, the join columns that lead to other Terms, SQL attributes with their query count, history), `GET /sources/{id}/graph?layer=semantic|data`, `GET /sources/{id}/path`, `PATCH /terms/{id}` (edit, rename, certify, through M5.1's `edit_term` with the engine's embedder) and `POST /edits/{id}/undo`. Two tables join where a column of one has a semantic FK used in join paths to an attribute on the other, the edges join paths walk. The data layer draws those and the declared FKs. The semantic layer joins two Terms when their tables join, and a table that represents no Term, such as Chinook's PlaylistTrack, bridges each pair of its neighbours as one edge `via` that table, drawn dashed. Upstream's exploration graph links Terms that share any table, which joins every two FK targets of one table (Customer and Inventory through rental), so it isn't used. The join path is a breadth-first search over the semantic layer's edges, ties broken by name, so each hop is an edge on screen; upstream's `find_term_link_path` walks tables and columns and can skip a Term in the middle. The renderer lays the graph out with d3-force, run to rest with a fixed random source, and draws nodes as real buttons over an SVG of edges, as DESIGN.md §4.9 asks (44 px, focusable, a list fallback). sigma.js draws to WebGL, which gives none of that; it waits for a source large enough to need it (DESIGN.md §10.1). **M6.4 decided (2026-11-07): an import commits, then re-embeds as a `reembed` job; certification travels only with the text it vouches for.** `auto_ontology/dal/model_interchange.py` is upstream's with its signatures (its `dal_surface.json` entry is upstream's, and upstream's 21 tests pass against it). The document (`ontological/interchange/schemas.py`) adds a Term's `synonyms`, `name_certified` and `description_certified`, `certified` on column and SQL attributes, and `description_certified` on tables and columns, each defaulting to what the store holds unset, so upstream's documents still read. An import keeps upstream's matching: an entity the store already holds is adopted as it is, and the new fields, like the names and descriptions, are written only onto rows it creates. SQL resolves with the engine's parser against the database's catalog, with the dialect its source kind names, and its statement is written as compile writes a SQL attribute's; both are imported when used, so the vendored DAL still loads without sqlglot. Ossie goes through the converter pinned to upstream's commit (`cb4b46b`). Its Ossie model carries the whole native document in a custom extension, so an Ossie import takes synonyms and the flags back from that snapshot by id, where the name, description or SQL they certify is unchanged: a description edited in another tool comes back uncertified. Once the import commits, `POST /model/import` starts a `reembed` job for each database it wrote, through the engine's `Jobs`, and answers. The job is M5.1's: `sync_database` embeds the semantic texts that aren't current, which carries `certified` onto the vectors, and the data layer is replaced when a row is another model's or its texts aren't the catalog's now (before, only another model's). Custom analyses import with their SQL but aren't embedded, as nothing searches them yet (M5.3). Not done here: the Settings → Import/Export screen and the compile-end YAML snapshot in `backups/` (§5.7). The import's `ops.change_log` rows came after (below).

**Compile and import logged (2026-11-07): what a recompile changes, and what an import creates, are edits by `compile` and `import`.** Both write through the vendored DAL in their own transaction, so `curate/edits.py` gives them `fields_of`, which reads and locks each row's logged fields before the write, and `log_write`, which logs each field that differs after it as one edit per Term, holding the Term's fields and its attributes'. A compile's pack takes its table's Terms and attributes before `_commit` writes them; what it creates isn't logged, since a first compile would log every field of the ontology and the Term's `created` already says when it was compiled. The first recompile of a table does log a change to each sampled attribute's description: it reads the generated description back as the column's own and appends the samples suffix the first compile left off. After that, a recompile with the same answers logs nothing. An import logs each Term and attribute it creates from `CREATED` (no name or description, no synonyms, uncertified), so each field the document gave it is a change, and a second import of the same document logs nothing. Undo refuses an edit that created a row (`Creation`, a 409), as there is no name to put back, and the Term editor offers no Undo for it; its history reads "Import created it as …". The rows a replacing import deletes aren't logged.

### S2: How long does a spawn take? (2026-11-04)

**What ran.** `tools/spikes/s2_spawn_time.py` on macOS arm64, with Claude Code 2.1.318 and `claude-agent-sdk` 0.2.178. It made 20 calls each on `haiku`, `sonnet` and `opus`, back to back, one fresh `query()` per call, so each started a new `claude` process. The call was one line, "Classify the column `customer_email` as one of: identifier, contact, measure, date.", with a one-field JSON schema, the §6.2 options and `effort="low"`. All 60 calls returned valid `structured_output`.

The script splits each call into three timings:

- **spawn**, from calling `query()` to the CLI's `init` message. This covers the SDK's `claude -v` check, starting the process and the initialize handshake.
- **the CLI's turn**, `ResultMessage.duration_ms`.
- **close**, from the `ResultMessage` until the process exits and `query()` returns.

Overhead is spawn plus close. `duration_api_ms` can't be used to work out overhead. It counts API requests the CLI sends while it is still starting up, so it often comes out longer than `duration_ms`.

| Model | `query()` p50 / p95 | spawn p50 / p95 | close p50 / p95 | overhead p50 / p95 | CLI turn p50 / p95 |
|---|---|---|---|---|---|
| haiku | 1.87 / 3.17 s | 0.17 / 0.21 s | 0.34 / 0.44 s | 0.53 / 0.61 s | 1.36 / 2.62 s |
| sonnet | 1.99 / 2.26 s | 0.17 / 0.25 s | 0.33 / 0.40 s | 0.53 / 0.58 s | 1.45 / 1.78 s |
| opus | 3.02 / 5.64 s | 0.18 / 0.23 s | 0.33 / 0.43 s | 0.55 / 0.62 s | 2.50 / 5.24 s |
| all 60 | 2.09 / 4.08 s | 0.17 / 0.23 s | 0.34 / 0.43 s | 0.53 / 0.62 s | 1.57 / 3.49 s |

The first call on each model was not much slower. Spawn took 0.35 s on the first `sonnet` and `opus` calls, against 0.17 s after that. Whole `query()` time varies with the model, mostly on `opus`, where one call took 8.2 s. Overhead hardly varies.

**Decision: no warm pool.** The rule asks whether a spawn takes more than 1.5 s at p50. It takes 0.53 s, spawn and close together. The whole `query()` is above 1.5 s at p50 (2.09 s), but that is the model's time, and a warm pool can't remove it. A pre-spawned client would save the 0.17 s spawn. The 0.34 s close could also be saved without a pool, by not waiting for the process to exit. Neither is worth the pool's complexity in M1.

**ARCHITECTURE.md changed.** §6.5's estimate said each call costs "a few seconds of process startup" and that split might add 20–30 minutes. It now gives 0.53 s of overhead per call, about 1.5–2 minutes of overhead for split's extra calls on a 200-table database. §3's per-call cost note now says the same.

**Result: all 8 cases pass, 149 checks, in about 30 s.** Every full run since the last change has given the same result.

| Case | What it checks | Result |
|---|---|---|
| First launch | `initdb` and start take 0.64 s. UTF-8, locale `C`, no TCP, 128 MB, 30 connections, a 0700 socket directory, `vector` and `pg_trgm`, every `host` line in `pg_hba` set to `reject`. | Crash | `kill -9` of the engine and then the postmaster. The next start replays WAL, and committed rows survive | pass |

**Decision.** The lifecycle works with the binaries S4 ships. It needed these changes, and §5.3 now says each one:
- Adopting checks that the process is named `postgres` and that `SHOW data_directory` through the advertised socket gives this data directory. A live pid alone is not enough. If the server isn't ours, the engine deletes `postmaster.pid` and the socket's lock file, which carries the same pid. It decides that only on positive evidence: a dead pid, a process that isn't `postgres`, another data directory, or a socket that is missing or refuses connections. Any other connection error raises. The first version of `pg.py` treated any error it didn't recognise as stale, so a full server would have lost its lock files. Hydra's review caught that too.
- An `flock` on `<appData>/pg.lock` covers initdb, start, adopt and stop.
- `initdb` uses `--auth-local=trust --auth-host=reject`, not `-A trust`. The whole first launch (initdb, start, creating the store, stop) runs in `pgdata.initdb/`, which becomes `pgdata/` only once the store exists. Hydra's review caught the first version, which renamed the directory right after `initdb`. A crash before the store was created then left a `pgdata/` that every later start took as complete. The extra stop and start make first launch 0.2 s slower.
- A restore goes into a new database, `ontological_restore`, which replaces the store only after `pg_restore` succeeds. Every start finishes or discards a restore that a crash interrupted. Hydra's review caught the first version, which dropped the store before restoring. `pg_restore --clean` can't be used, and the engine's connection pool reconnects afterwards.
- Dump names use one UTC clock read, so they sort correctly across time-zone and DST changes. Pruning keeps the newest 10 and never removes the dump just written. §5.3 Disk now points to that rule, which §5.7 already had, so the two sections no longer contradict each other.
- Dumps are written under a temporary name and carry their kind in the file name. A dump counts as current for a major-version move only if it is a quit dump, newer than the old server's last start, and the old server stopped cleanly. If the old server is still running, the engine dumps it live. The new cluster is built and restored in `pgdata.upgrade/` and only swapped in once it is complete, so a crash or a failed restore never leaves an empty store in `pgdata/`. The first version of `pg.py` moved `pgdata/` aside before running `initdb`. A crash in between made the next start take the first-launch path and create an empty store. Hydra's review caught it.

For M0.3: `pg.py`'s structure carries over (`Layout`, `inspect_pid_file`, `ensure_running`, `stop`, `migrate`, `restore`, `upgrade_major`, `resume_upgrade`), and so does `run.py`'s case list, as the §12 lifecycle tests. Three things the spike left out: real Alembic chains in place of the SQL-string revisions, the disk-full pause, and the 103-byte socket path limit. Under `/Users/<name>/Library/Application Support`, that limit allows a home folder name of up to 33 bytes. `pg.py` refuses a longer path and says why.

**ARCHITECTURE.md changed.** §5.3 adds Lock, Stale lock files, Second engine and Dumps, and rewrites First launch, Start, Adopt, Migrations and Major-version upgrades. §5.1 adds `pg.lock` and the dump kinds.

### S7: embedder loader and speed (2026-11-04)

Ran `uv run tools/spikes/s7_embedder.py` on an Apple M5 Max (18 cores, 64 GB, macOS 26.5.2) with onnxruntime 1.31.1, against `snowflake-arctic-embed-m-v1.5` at `e58a8f7`, file `onnx/model_int8.onnx` (110.1 MB). The raw numbers are in `tools/spikes/s7_results.json`.

**Loading.** Both loaders load the file offline from a local directory. fastembed 0.9.1 has no v1.5 entry, so it loads only as a custom model (`add_custom_model`, CLS pooling, `output_name="token_embeddings"`). On the same batches the two give the same vectors (min cosine 0.9999998 over 256 passages and 8 queries). Load takes 0.11 s direct and 0.18 s through fastembed, plus about 2 s for fastembed's imports on a cold start.

**int8 vectors depend on the batch.** The graph quantizes activations per batch (`DynamicQuantizeLinear`), so a passage's vector shifts with its batch-mates and their padding: min cosine 0.996 against the same text embedded alone. The engine embeds each query alone, so query vectors are deterministic.

**Batch cost is linear in padded tokens.** Past about 256 tokens a batch runs at 10.6–12 tokens/ms at every shape from 16×64 to 512×4, so larger batches buy no throughput. The slowest rate, 10.6 tokens/ms, puts 100 ms at 1,057 padded tokens.

| Bulk run, 10⁵ synthetic catalog texts (p50 51 tokens, max 125) | Time | Texts/s |
|---|---|---|
| Direct, sorted by length, batches capped at 1,057 padded tokens | 430 s | 232 |
| Direct, input order, 8 texts per batch | 678 s | 148 |
| fastembed, input order, `batch_size=8` | 651 s | 154 |

| Query latency (ms), 200 queries at random times | p50 | p95 | max |
|---|---|---|---|
| Idle, direct / fastembed | 3.3 / 3.3 | 3.8 / 4.3 | 5.7 / 6.0 |
| Priority worker, bulk batches at the cap (≈91 ms each) | 50 | 88 | 136 |
| Priority worker, bulk batches at 4× the cap (≈350 ms) | 266 | 335 | 353 |
| Concurrent `run` on the same session, batches at the cap | 6.7 | 7.6 | 8.7 |
| Concurrent `run` on the same session, batches at 4× the cap | 5.7 | 7.4 | 10.3 |

A one-off check (not in the script) of other files and providers on a 16×64 batch: int8 on CPU 12.6 tokens/ms, fp32 11.1, fp16 7.3; the CoreML provider 2.5–2.8 for every file, because it can't compile the graph's dynamic shapes and splits it.

**Decision.**
- Loader: direct `onnxruntime` + `tokenizers`, int8 on the CPU provider. fastembed works but only as a custom model, adds 15 MB and 8 packages to the bundle (126 → 141 MB of site-packages), and batches by count in input order behind a session it hides. The engine needs length-sorted, token-capped batches (+57% throughput) and concurrent calls into one session.
- Queries don't queue behind bulk work: they call the session concurrently and wait about 7 ms whatever the batch size. The priority queue in §5.6 is dropped.
- Bulk batch cap: 1,024 padded tokens (batch size × longest text after sorting), about 95 ms here. It keeps cancellation and progress fine-grained, and bounds a query to one batch if a queue is ever needed. Smaller Macs do fewer tokens per ms, so M1.5 calibrates the cap at engine start from one timed batch, targeting 100 ms.
- A full 10⁵-text embed takes about 7 minutes on this machine and longer on smaller ones. It runs as a background job.

Changed ARCHITECTURE.md §5.6 (Embedder) and §7.1. Not measured: a smaller Mac, and int8 recall against fp32 (the retrieval benchmark, §7.4, covers quality).

### S8: How long does a `bm25s` rebuild take at 10⁵ documents? (2026-11-04)

**What ran.** `tools/spikes/s8_bm25s_rebuild.py` with `bm25s` 0.3.16, numpy 2.5.4 and Python 3.12.13, on an Apple M5 Max. It ran twice with the defaults: 10⁵ synthetic table and column documents over 10 databases, 5 repeats, and 1,000 queries at k=50. Each document is name + synonyms + description, as §7.3 indexes them. Identifiers come in snake_case, camelCase, PascalCase and UPPER_SNAKE, with glossary abbreviations and acronyms in them, and descriptions run one to three sentences with a long tail of made-up words. That gives 1.84 M tokens, 18 tokens per document at p50 (29 at p95), a 22,128-token vocabulary and a 14 MB index.

The tokenizer is the §7.3 one: split on snake_case and camelCase, lowercase, expand glossary acronyms, drop stopwords, with the same function on queries. Planted documents check it: `cust_acct_no` ranks first for "customer account number" and for `cust_acct_no`, `ZorblaxInvoiceLineID` for "zorblax invoice line id", and `QUUXTREL_SKU_QTY` for "quuxtrel SKU qty" and "quuxtrel stock keeping unit quantity".

| Step | Run 1 p50 / max | Run 2 p50 / max |
|---|---|---|
| tokenize 10⁵ texts | 0.80 / 0.87 s | 0.82 / 0.96 s |
| `BM25.index` on the tokens | 0.89 / 0.93 s | 0.76 / 1.24 s |
| **full rebuild** (tokenize + index) | **1.73 / 1.75 s** | **1.49 / 2.38 s** |
| one database's rebuild (~10⁴ docs) | 0.16 / 0.22 s | 0.17 / 0.31 s |
| query, k=50 | 0.40 / 1.19 ms | 0.36 / 0.83 ms |
| query while a full rebuild runs on a thread | 0.57 ms p50, 24 ms p95, 111 ms max | 0.76 ms p50, 18 ms p95, 83 ms max |

Run 2's maxima came while other sessions were busy on the same machine. Searches slow down during a rebuild because they share the GIL with it. They stay correct, because the new index replaces the old one by a single reference assignment. In both runs, every search during the rebuild used the old index and none saw a partly built one.

**Decision: rebuild on every change and swap atomically.** A full rebuild takes 1.5–1.7 s at p50 and at most 2.4 s, under the rule's 3 s. Per-database indexes and debounced edits aren't needed. Searches cost under a millisecond, and up to about 0.1 s while a rebuild is running, which is small next to a tool call's turn. For M3.6:
- Run at most one rebuild at a time. A change that arrives during a rebuild marks the index stale, and one more rebuild runs after the current one, so a burst of compile writes costs two rebuilds, not one per write.
- Cache each document's tokens by `content_hash`, so a rebuild tokenizes only changed documents. That removes about half of a rebuild (the tokenize row).
- The numbers come from one fast machine. A slower Mac is the main risk to the 3 s margin. If a full rebuild there goes past about 3 s even with cached tokens, fall back to the per-database indexes measured above.

**ARCHITECTURE.md changed.** §7.3 said a rebuild "should take about a second". It now gives the measured 1.5–1.7 s and the policy above.
